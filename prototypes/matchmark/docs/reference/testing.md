# Testing the generator

How Matchmark proves what it generates, layer by layer. Cross-checked against Parquet.SourceGenerator, which tests a
generator the same way at the layers that apply. Each layer catches a failure the others can't, so together they stand
in for a golden-file suite, which Matchmark deliberately doesn't have: generated output is **derived and diffed, never
committed** (Diffra's approach to generated assets).

| Layer | Proves | Built as |
|:--|:--|:--|
| 1. The model | The decisions every output is a function of: names, types, outcomes, support | `ApiModelTests`, from small specs, independent of any output |
| 2. Incrementality | An edit re-runs only what it touches | `IncrementalityTests`, from Roslyn's step tracking on the named steps (`TrackingNames`) |
| 3. Diagnostics | Each one fires where it should, and the reference matches the descriptors | the diagnostic tests; `DiagnosticDocsTests` |
| 4. Generated code is code | It parses, compiles and loads, for every sample and the large specs, with no warning | `GeneratedServer`, the corpus, `LargeSpecTests`, `EmittedCodeTests` |
| 5. Behaviour | The generated server, client and fake do what the spec says, read as an independent validator reads it | the spec's own regression suite run against each generated server; the round-trip check of ASP.NET Core's served document; `OracleTests` |
| 6. Derived evidence | What changed, for review, against the pull request's base | `DerivedEvidenceTests` and CI's `derived` job |
| 7. Breadth | Every construct in every supported version | the official examples (57 of 57), GitHub's and Stripe's specs, the support matrix, `RandomSpecTests` |
| 8. Consumption | It works as a package and an image | `eng/consume-package.sh` (CI's `package` job); the container image job |

## 1. The model

`ApiModel.Read(spec)` gives what the emitter decides: each operation's parameters (typed, with where they bind from), body
and outcomes, and the diagnostics. Tests pin these from small specs. A test that asserts a substring of generated text
pins an implementation detail instead; new ones go here, or to the derived evidence.

## 2. Incrementality

The pipeline's steps are named (`TrackingNames`: specs, shapes, references, referenced resolvers, tag slices). The tests reuse
one driver across edits and assert what each step did:

- an edit to C# that isn't a spec: every step and every output reused;
- a spec with a comment or blank lines added: the text changed, the slices didn't, so no tag re-emits;
- an edit to one tag's operation: exactly one slice modified, one reused, and only that tag's file re-emitted;
- an edit to a component one tag uses: only that tag's slice and file change, because slices keep only what their tag reaches;
- an edit to an endpoint, with Verify on: the comparison runs again, and the parse step (`Matchmark.Shapes`) is reused;
- an edit to a summary, with Verify on: the spec's text changed, and its shape didn't, so nothing after the parse runs;
- the same input twice: the same bytes (generated code is commit-deterministic).

## 3. Diagnostics

Every descriptor is in [diagnostics](diagnostics.md) with its severity and title, and every id there is one the generator
has or is marked retired (`DiagnosticDocsTests`). Its first run found MM029's title out of step.

## 4. Generated code is code

`EmittedCodeTests` compiles every sample's generated code at every warning level, nullable included, with each outcome
style. The baseline is empty and must stay empty, because a warning in code the consumer didn't write is a generator bug.
The compiler hides nullable warnings in an `<auto-generated/>` file unless the file turns them on, so the gate also
asserts that every source has `#nullable enable`. Without that, it would pass on anything.

## 5. Behaviour: the independent oracle

The generator, engine and twin read schemas the same way, so a misreading they share would pass every other test.
`OracleTests` gives every sample's component schemas to Corvus.Json.Validator, a JSON Schema 2020-12 validator written
apart from Matchmark (Apache-2.0; JsonSchema.Net was passed over for its maintenance-fee licence). The values come from
Matchmark's own `Samples`: a full and a minimal sample, the boundaries and the violations. Matchmark's `SchemaValidator`
and the oracle must agree on each one. The oracle must also find every sample valid and every violation invalid, so a
broken translation can't pass. The ten samples give about 1,250 values. The whole spec compiles once: its schemas go in
`$defs`, with a root property for each.

Its first run disagreed on the Pet Store's `PetDetails`: `{"kind":"not-a-kind","goodBoy":true}` was valid to the oracle
and invalid to Matchmark. Matchmark was right. OpenAPI 3.1.1 says a discriminating value that matches no mapping
determines no schema, and that "validation SHOULD fail". JSON Schema has no discriminator, so the test writes it as
JSON Schema for the oracle: the property is required, is one of the mapped names, and each name selects its schema. That
translation is the one place where the oracle reads OpenAPI rather than JSON Schema, and it is written out in the test.

## 6. Derived evidence

Per sample (every `samples/*/openapi.yaml` with its overlays, the split sample from its bundle, and the Pet Store),
`DerivedEvidenceTests` writes, to `MATCHMARK_DERIVED`:

| File | What it is | A change means |
|:--|:--|:--|
| `{sample}.model.json` | the model: operations, parameters, bodies, outcomes, diagnostics | a decision changed: review it |
| `{sample}.api.txt` | the generated public surface, signatures only, in a stable order | the API consumers compile against changed: review it |
| `{sample}.g.cs` | every generated source | a body changed: information, unless the surface or the model did too |

On a pull request, CI derives the head and the merge-base (in a worktree) and puts the counts and the model and surface
diff in the run's summary. A base that can't be derived is reported as unavailable, never as a pass. Nothing is
committed, so no golden file churns, and nothing compares the pull request against itself.

**Next** (Diffra's model): a required check bound to the digest of the reviewed change, so an approval goes stale when
the output changes again; the derived files as Diffra evidence once its CLI is released.

## 7. Breadth: random specs

`RandomSpecTests` generates seeded specs and compiles what each one generates. The specs vary what broke GitHub's and
Stripe's builds:

- parameters named like the generated code's own names;
- parameter lists longer than `Func` takes;
- shared responses and request bodies;
- enums, nested objects, unions and constraints;
- several tags.

When a spec fails, the test shrinks it to the fewest operations and parameters that still fail, and prints it so it can
be committed as a fixture. `MATCHMARK_RANDOM_SPECS` sets how many seeds run (12 by default). Its first run found a query
parameter named `body` clashing with the request body's parameter. Parameter names are now decided once, in the model,
away from the generated signatures' own names and from each other. 200 seeds then passed.

## 8. Consumption

`eng/consume-package.sh` packs the generator and builds a fresh project outside this repository's build files. The project
references only the package, marks the Pet Store spec, and treats warnings as errors. Its `Program` calls the generated
`MapPetstore`, so the build fails unless the package delivers three things: a generator that runs, the assemblies it loads
beside it, and the props that make the metadata visible. CI runs it as the `package` job, and the image job does the same
for the container.

## Benchmarks

`Matchmark.Benchmarks` (BenchmarkDotNet) times the deterministic stages, so a slow test, or a claim about speed, is
measured rather than guessed. `GeneratorStages` covers reading a spec, normalising it, the parse step's `ApiShape`, the
read-only model, and a whole generator run. `EngineStages` covers the suite, sampling and validating every component
schema, and the violations of every sample. Each runs on the Pet Store, and on GitHub's and Stripe's specs when they've
been fetched. Run it with `dotnet run -c Release --project Matchmark.Benchmarks -- --filter '*'` (add `--job short` for a
quick look).

First numbers, from short jobs on this container's 4 cores, with tests running alongside, so take them as orders of
magnitude:

| Stage | Pet Store | GitHub (1,272 operations) | Stripe (612) |
|:--|--:|--:|--:|
| Read (Microsoft.OpenApi) | 0.65 ms | 0.37 s | 0.29 s |
| Normalise | 1.1 ms | 0.49 s | 0.41 s |
| Parse to `ApiShape` | 1.7 ms | 0.73 s | 0.38 s |
| A whole generator run | 6.1 ms | 2.7 s | 2.1 s |
| The suite (`RegressionSuite.FromJson`) | | 2.8 s | |
| A sample of every schema, validated | | 1.8 s | |

The violations were the outlier, and they're why the oracle over the large specs took so long. Each violation deep-copied
every object above the change, then validated and serialised the whole value to drop duplicates. That is quadratic in a
value's size: GitHub's `issue` sample is 19 KB, has 1,386 violations, and took 1.4 s alone. Now a violation is judged by
the changed part alone when nothing above it judges the value as a whole (no `oneOf`, `anyOf`, `allOf`, `not`, `if`,
`enum`, `const`, `uniqueItems`, `contains` or discriminator above it). It's told apart from others by its path and
value, and the whole is built once, from one copy. The output is the same: a fingerprint of every violation and boundary
is identical before and after over all the samples and every GitHub schema (411,567 variants). Every violation
and boundary of every GitHub schema took 245 s and now takes 45 s (5.4 times faster); Stripe's 58,040 take 21 s.

## Learned from Parquet.SourceGenerator

Taken: diagnostics as equatable data with positions; step-level incrementality tests on reused drivers; an "examined N"
assertion in every gate so an empty run can't pass; signature-only surface renderings, with a signature change needing
review and a body change not; derived outputs diffed against the base rather than committed.

Taken since: the emitted-code gate (compiler warnings; analyzers treat generated code as generated, so the compiler's
own checks are what a consumer can't opt out of); random specs, shrunk on failure; the packed-package consumption test; the independent oracle.

Next to take: random specs regressed against the twin as well as compiled; the oracle over the large specs' schemas.

Avoided: its 4.0.1 Roslyn floor (Matchmark is on 4.14, so steps carry tracking names); a parser and an emitter of 2,400
lines each (Matchmark's emitter is split by output, the largest file under 900 lines).
